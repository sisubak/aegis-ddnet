## 2. Как устроено кодирование яркости (L)

И в 0.6, и в 0.7 кастомный цвет — это упакованный HSL, где байт L — это НЕ реальная яркость, а «сжатая» яркость в диапазоне `[Darkest, 1.0]`:

- 0.6: `L_real = 0.5   + (byte/255) * 0.5`      → диапазон [0.5, 1.0]
- 0.7: `L_real = 0.239 + (byte/255) * 0.761`    → диапазон [0.239, 1.0]

То есть 0.7 допускает более тёмные цвета (до 0.239), а 0.6 физически не может быть темнее 0.5.

## 3. Разбор математики FromSixup

Пошагово для тела:

1. `ColorHSLA(packed)` — конструктор из `unsigned` (`color.h`, стр.75-81) читает байты как H,S,L (alpha=false → a=1). Значит `l = byteL/255` — это СЖАТАЯ 0.7-яркость.
2. `.UnclampLighting(DARKEST_LGT7)` → `L_real = 0.239 + l*0.761` — корректная распаковка в реальную яркость 0.7.
3. `.Pack(DARKEST_LGT)` → `L6 = clamp((L_real - 0.5)/0.5, 0, 1)` — упаковка в 0.6.

Само по себе преобразование диапазонов **симметрично и по L корректно** (это точная инверсия `ToSixup`). Для цветов с `L_real >= 0.5` яркость сохраняется 1:1.

### Найденная проблема (root cause)

`std::clamp(..., 0.0f, 1.0f)` в `Pack(Darkest)` при `L_real < 0.5` жёстко схлопывает результат в 0 → в 0.6 цвет становится максимально тёмным (`L_real == 0.5`). Все 0.7-цвета из «расширенного тёмного диапазона» [0.239, 0.5) сваливаются в одну точку и выглядят темнее оригинала. Это и есть эффект «становится слишком темно», описанный в issue (ddnet 0.7 `#c367be` → ddnet 0.6 темнее, чем teeworlds-эквивалент).

Дополнительный вклад в «затемнение»:

- **Насыщенность (S) не ремапится.** В 0.6 отрисовка тела домешивает L через свою кривую, и при переносе только L без коррекции S визуально тёмные насыщенные цвета уходят в грязь. S переносится байт-в-байт, хотя связка (S,L) в двух протоколах даёт разный воспринимаемый цвет.
- **Потеря информации о цветах ниже 0.5** необратима в рамках одного L-байта 0.6 — 0.6 просто не умеет их показать. Полное совпадение с 0.7 для очень тёмных цветов недостижимо; задача — минимизировать ошибку, а не устранить.

## 4. Кандидат-фикс (НЕ ПРИМЕНЯТЬ, обсудить)

Основная цель: убрать резкое схлопывание тёмных цветов в чёрный и сделать преобразование через полноценный HSL→RGB→HSL roundtrip, чтобы сохранить воспринимаемый оттенок, а не только L-байт.

### Вариант A (минимальный, только смягчить клэмп по L)

Оставить существующую логику, но проблема — в `Pack(Darkest)` клэмп нельзя убрать (иначе получим отрицательный L / переполнение при упаковке). Поэтому чистый L-only путь принципиально не может показать цвета темнее 0.5 — вариант A ничего кардинально не чинит. Годится только как «оставить как есть, задокументировать ограничение».

### Вариант B (рекомендуемый — конверсия через RGB, сохраняем оттенок)

Идея: распаковать 0.7-цвет в реальный HSL, перевести в RGB (реальный видимый цвет), затем взять HSL этого RGB и упаковать в 0.6. Для L < 0.5 вместо схлопывания в чёрный — понизить насыщенность/поднять L так, чтобы сохранить оттенок при минимально допустимой для 0.6 яркости.

Псевдо-набросок (требует доработки и тестов):

```cpp
auto ConvertColor7to6 = [](int packed7) -> int {
    ColorHSLA hsl7 = ColorHSLA(packed7).UnclampLighting(ColorHSLA::DARKEST_LGT7); // реальный HSL 0.7
    // если цвет темнее, чем 0.6 умеет — сохраняем оттенок, поджимая S, а не гасим в чёрный
    if(hsl7.l < ColorHSLA::DARKEST_LGT)
    {
        // компенсируем недобор яркости уменьшением насыщенности,
        // чтобы воспринимаемая "тёмность" осталась близкой
        float deficit = (ColorHSLA::DARKEST_LGT - hsl7.l) / ColorHSLA::DARKEST_LGT;
        hsl7.s = std::clamp(hsl7.s * (1.0f - deficit), 0.0f, 1.0f);
        hsl7.l = ColorHSLA::DARKEST_LGT;
    }
    return hsl7.Pack(ColorHSLA::DARKEST_LGT); // упаковка в 0.6-диапазон
};
m_ColorBody = ConvertColor7to6(m_aUseCustomColors[protocol7::SKINPART_BODY] ? m_aSkinPartColors[protocol7::SKINPART_BODY] : 255);
m_ColorFeet = ConvertColor7to6(m_aUseCustomColors[protocol7::SKINPART_FEET] ? m_aSkinPartColors[protocol7::SKINPART_FEET] : 255);
```

Коэффициент компенсации S — эвристика, требует подбора по скриншотам (ddnet 0.7 / teeworlds 0.7 как эталон, ddnet 0.6 как результат).

### Что проверить перед фиксом

1. Как именно 0.6-клиент домешивает L при отрисовке тела (`CRenderTools` / рендер tee) — чтобы понять, компенсировать S или L.
2. Соответствует ли `ToSixup` (обратное направление) — фикс должен оставаться примерно обратимым для цветов из общего диапазона [0.5, 1.0], чтобы roundtrip 0.6→0.7→0.6 не менял цвет.
3. Регресс на стандартных скинах (STANDARD_SKINS) — они матчатся по имени раньше, кастом-цвет к ним обычно не применяется, но проверить нужно.
