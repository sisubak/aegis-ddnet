## 1. Проблема (кратко)

При коллизии пользовательского save-кода логика "two tries" молча переключалась на
авто-сгенерированный код и выставляла `SAVE_SUCCESS`. Игрок не получал никакого
уведомления, что его выбранный код был занят. Ветка ошибки на строках 1842-1849
("This save-code already exists") недостижима в этом сценарии, т.к. она срабатывает
только если ОБА кода — дубликаты.

Вариант A из аудита (`p_savecode.md`) выставлял `SAVE_WARNING` ДО ретрая, из-за чего
успешный ретрай перезаписывал статус на `SAVE_SUCCESS` (строка 1812) и предупреждение
терялось. Это неверно.

## 2. Корректный фикс

Ввёл локальный флаг `UserCodeTaken`, который запоминает, что пользовательский код был
занят. Предупреждение выставляется НЕ до ретрая, а ПОСЛЕ успешной вставки под авто-кодом
— так статус `SAVE_WARNING` + сообщение уже не перезаписываются.

### Изменение 1 — объявление флага (перед циклом do/while)

old:
```cpp
	bool Retry = false;
	// two tries, first use the user provided code, then the autogenerated
	do
	{
```
new:
```cpp
	bool Retry = false;
	// remember if the user provided code was already taken, so we can warn
	// the player even after successfully falling back to the generated code
	bool UserCodeTaken = false;
	// two tries, first use the user provided code, then the autogenerated
	do
	{
```

### Изменение 2 — установка флага в ветке ретрая и warning после успеха

old:
```cpp
		if(NumInserted == 1)
```

new:
```cpp

		{
			pResult->m_Status = CScoreSaveResult::SAVE_SUCCESS;
			if(UseGeneratedCode)
			{
				pResult->m_aCode[0] = '\0';
			}
			if(w != Write::NORMAL)
			{

		{
			UseGeneratedCode = true;
			Retry = true;
			UserCodeTaken = true;
```

## 3. Почему это безопасно и корректно

- Логика фолбэка сохранена: команда всё равно сохраняется под авто-кодом (данные не
  теряются) — регрессии поведения нет.
- `SAVE_WARNING` выставляется ТОЛЬКО в случае `w == Write::NORMAL` (else if внутри
  `if(w != Write::NORMAL)`), т.е. не конфликтует с `SAVE_FALLBACKFILE` (резервный файл
  при обрыве БД). Порядок ветвлений гарантирует приоритет FALLBACKFILE.
- Статус выставляется ПОСЛЕ успешной вставки, поэтому успешный ретрай его больше не
  перезаписывает на `SAVE_SUCCESS`.
- Блок ошибки на строках 1842-1849 не тронут: он по-прежнему корректно ловит случай
  двойного дубликата (оба кода заняты), т.к. `SAVE_WARNING` входит в список допустимых
  статусов и не переводится в `SAVE_FAILED`.

## 4. Проверка доставки сообщения игроку

Проверил цепочку `SAVE_WARNING` → игрок:

1. `teams.cpp:1162-1164`: `CScoreSaveResult::SAVE_WARNING` → `State = SAVESTATE_WARNING`.
2. `teams.cpp:1177-1188`: `SendSaveCode(...)` вызывается (State != -1), и т.к.
   `State != SAVESTATE_DONE`, в параметр `pError` передаётся `m_aMessage`
   (наше предупреждение), а не пустая строка.
3. `gamecontext.cpp:4822-4926` `SendSaveCode`:
   - Новым клиентам (`>= VERSION_DDNET_SAVE_CODE`) строка `pError` уходит в самом
     `NETMSGTYPE_SV_SAVECODE` (`Msg.AddString(pError)`, строка 4828) → сообщение доходит.
   - Старым клиентам ветка `case SAVESTATE_WARNING:` (строка 4917-4919) делает
     `str_copy(aBuf, pError)` и `SendChatTarget(MemberId, aBuf)` → сообщение доходит.

Вывод: `SAVE_WARNING` корректно доносит текст до игрока в обоих клиентских путях,
поэтому дополнительный путь (например через FALLBACKFILE/broadcast) не нужен.

Также при warning `pResult->m_aCode` уже обнулён (строка 1815, т.к. `UseGeneratedCode`
на второй попытке == true), поэтому игроку в сообщении о загрузке подставится
именно `pGeneratedCode` — рабочий код, под которым реально сохранена команда.
