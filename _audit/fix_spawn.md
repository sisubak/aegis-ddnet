# Аудит: Issue #5408 — тичи спавнятся рядом со spawn-точкой вместо самой точки

СТАТУС: ANALYZED — НЕ ПРИМЕНЕНО (fix-changes-physics/gameplay, только анализ)

Файл: `src/game/server/gamecontroller.cpp`
Функции: `CanSpawn` (стр. 168), `EvaluateSpawnType` (стр. 105), `EvaluateSpawnPos` (стр. 89).

## Как работает выбор спавна

### CanSpawn (168)
Создаёт `CSpawnEval Eval` и последовательно вызывает `EvaluateSpawnType` для
DEFAULT/RED/BLUE. Итоговая точка — `Eval.m_Pos`, флаг успеха — `Eval.m_Got`.

### EvaluateSpawnPos (89) — расчёт Score
```
Score = сумма по всем колайдящим тичам: (d==0 ? 1e9 : 1/d)
```
где `d = distance(Pos, персонаж)`. Чем **ближе** чужие тичи, тем **выше** Score.
Точное совпадение (d==0) даёт штраф 1e9. Выбирается точка с **минимальным** Score
(см. `pEval->m_Score > S` в стр. 158) — то есть максимально свободная.

### EvaluateSpawnType (105) — вот здесь корень проблемы
Ключевой блок в ветке `j == 0` (поиск пустого слота), стр. 129–154:
```cpp
vec2 aPositions[5] = {(0,0), (-32,0), (0,-32), (32,0), (0,32)}; // center,left,up,right,down
int Result = -1;
for(int Index = 0; Index < 5 && Result == -1; ++Index) {
    Result = Index;
    if(!PlayerCollision || PlayerCollisionDisabled) break; // спавн строго в центр
    for(...чужие тичи...) {
        if(CheckPoint(SpawnPoint + aPositions[Index]) ||
           (CanCollide && distance(pChr->m_Pos, SpawnPoint+aPositions[Index]) <= ProximityRadius))
        { Result = -1; break; } // позиция занята — пробуем следующую из aPositions
    }
}
if(Result == -1) continue; // точка целиком занята — пропускаем к j==1
P += aPositions[Result];   // <-- СМЕЩЕНИЕ на соседний тайл
```

## Почему выбирается точка РЯДОМ, а не сама точка

1. При `j == 0` алгоритм не просто проверяет саму spawn-точку, а перебирает
   **5 позиций**: центр и 4 соседних тайла (±32 px = 1 тайл). Если центр (Index 0)
   занят колайдящим тичем в радиусе `GetProximityRadius()`, `Result` сбрасывается
   в -1 и цикл переходит к смещённой позиции (left/up/right/down).
2. Как только находится свободная соседняя позиция, к точке прибавляется
   `aPositions[Result]` (стр. 154) — тич спавнится на **соседнем тайле**, а не на
   самой spawn-точке. Это и есть наблюдаемое поведение из issue.
3. Смещение срабатывает ТОЛЬКО когда включён `PlayerCollision` и у игрока не
   отключены коллизии. При `!PlayerCollision || PlayerCollisionDisabled`
   (типичный DDrace/DDNet режим) — `break` на Index 0, спавн строго в центр точки.
   Поэтому баг проявляется в режимах с включёнными коллизиями игроков.
4. Если все 5 позиций заняты — точка пропускается, и в `j == 1` берётся любая
   точка «как есть» (без offset-проверки), где Score может дать 1e9 при наложении.

## Что означало бы «спавнить всегда на точке» (fix — НЕ применён)

Чтобы тичи всегда спавнились строго на spawn-точке даже если она занята, нужно
убрать offset-логику: использовать только `aPositions[0]` / не прибавлять смещение
(фактически `P = SpawnPoint` всегда). Это меняет геймплей/физику:
- тичи начнут накладываться друг на друга на занятой точке (стек тичей);
- при включённом PlayerCollision это влияет на коллизии и стартовое расталкивание;
- меняется поведение выбора между несколькими spawn-точками (Score считается уже
  без учёта соседних свободных тайлов).

Поэтому изменение классифицируется как fix-changes-physics/gameplay и по заданию
НЕ вносилось. Здесь только анализ.

## Итог
Причина «спавна рядом» — массив `aPositions` из 5 позиций в `EvaluateSpawnType`
(ветка j==0): при занятом центре выбирается соседний тайл (±32px) и к позиции
прибавляется offset (стр. 131, 154). Score (`EvaluateSpawnPos`) лишь ранжирует
точки по близости чужих тичей и не является причиной смещения. Фикс потребовал бы
убрать offset — это правит геймплей, поэтому не применён.
