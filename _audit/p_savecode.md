## 3. Корень бага (мой разбор)

Логика "two tries" устроена так:

1. Если игрок задал свой код (`m_aCode` не пуст) и это `Write::NORMAL`, первая попытка
   идёт с пользовательским кодом (`UseGeneratedCode == false`).
2. Если пользовательский код уже занят (`NumInserted == 0`), ветка на строке 1823
   молча переключается на авто-код (`UseGeneratedCode = true; Retry = true`).
3. Вторая попытка почти всегда успешна (авто-код случайный, коллизия крайне
   маловероятна) → `m_Status = SAVE_SUCCESS`.

Следствие: когда пользовательский save-код дублируется, команда **молча** сохраняется
под авто-сгенерированным кодом, а игроку показывается успех — ветка на 1830-1838
(с сообщением "This save-code already exists") практически недостижима. Она срабатывает
только если ОБА кода (пользовательский И случайный авто-код) окажутся дубликатами, что
почти невозможно. Именно это и есть "duplicated save codes are not handled correctly /
the error message is not printed".

Дополнительно: строка 1774 инициализирует `pResult->m_aCode`, а строка 1812 обнуляет его
при `UseGeneratedCode`. При молчаливом фолбэке игрок получает авто-код без какого-либо
уведомления, что его выбранный код был отвергнут.

## 4. Можно ли дать дословный безопасный патч?

**Частично НЕЛЬЗЯ дать канонический патч**, и вот почему:

- В issue нет решения/PR — не зафиксировано, какое поведение считается правильным
  мейнтейнерами: (а) при коллизии пользовательского кода возвращать ошибку и НЕ сохранять,
  либо (б) молча фолбэчить на авто-код (текущее), но при этом хотя бы уведомлять игрока.
  Это продуктовое/дизайнерское решение, а не однозначный технический фикс.
- Ветка обработки ошибки (1830-1838) сама по себе не сломана — она недостижима из-за
  логики фолбэка выше. "Исправить печать сообщения" нельзя простой заменой одной строки:
  нужно менять поток управления в цикле `do/while`.
- Любой вариант затрагивает семантику `NumInserted`/фолбэка и поведение, видимое игроку
  (teams.cpp:1157-1188 маппит `m_Status` в `SAVESTATE_*` и отправляет сообщение через
  `SendSaveCode`). Менять это без согласованного дизайна рискованно.

**НО** есть один безопасный, локальный, дословный микро-фикс для реально сломанного
двойного-дубликата (когда авто-код тоже занят): убрать `else` из ветки ретрая, чтобы
исход последней попытки корректно детектировался. Однако это НЕ решает основную жалобу
(молчаливый фолбэк пользовательского кода) — оно лишь чинит недостижимость сообщения в
краевом случае. Полное решение основной жалобы требует изменения дизайна фолбэка и
согласования с мейнтейнерами → в этой части **НЕЛЬЗЯ** давать патч вслепую.

## 5. Предлагаемые варианты (для обсуждения, НЕ применять без решения по дизайну)

### Вариант A (минимальный, безопасный) — уведомлять игрока о фолбэке
Сохранить текущее поведение (фолбэк на авто-код), но при коллизии пользовательского кода
выставлять предупреждение, чтобы игрок понял, что его код был занят.

Файл: `src\game\server\scoreworker.cpp`

old_text (строки 1823-1827, дословно):
```cpp
		else if(!UseGeneratedCode)
		{
			UseGeneratedCode = true;
			Retry = true;
		}
```
new_text:
```cpp
		else if(!UseGeneratedCode)
		{
			UseGeneratedCode = true;
			Retry = true;
			pResult->m_Status = CScoreSaveResult::SAVE_WARNING;
			str_copy(pResult->m_aMessage, "This save-code already exists, using a generated one instead");
		}
```
Замечание: этот вариант выставляет `SAVE_WARNING` ДО ретрая; если ретрай успешен,
`m_Status` перезапишется на `SAVE_SUCCESS` на строке 1809, и предупреждение потеряется.
Чтобы сообщение сохранялось, нужно НЕ перезаписывать `m_Status` при уже установленном
`SAVE_WARNING` — это уже больше одной правки, т.е. не чисто-дословный однострочник.

### Вариант B (строгий) — при занятом пользовательском коде вернуть ошибку, без фолбэка
Требует убрать/переписать логику ретрая в цикле `do/while` (строки 1776-1828). Это
переработка потока управления, не безопасная дословная замена. **НЕ давать дословный
патч** — нужно согласование поведения.
