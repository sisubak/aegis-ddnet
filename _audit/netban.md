## 1. Амплификация serverinfo (отражённый DDoS)

### server.cpp:2710 (CServer::SendServerInfo) + server.cpp:3034-3086 (PumpNetwork, разбор SERVERBROWSE_GETINFO)
Проблема: классический reflection/amplification. Пакет-запрос `SERVERBROWSE_GETINFO`
(~9-14 байт) порождает ответ с полным списком игроков. Для `SERVERINFO_EXTENDED` и
`SERVERINFO_64_LEGACY` кэш разбит на несколько чанков (`for(const auto &Chunk : pCache->m_vCache)`),
и на ОДИН запрос уходит СРАЗУ НЕСКОЛЬКО UDP-пакетов (до NET_MAX_CONNLESS_PAYLOAD каждый).
В протоколе 0.6 адрес источника не верифицируется (нет security token), поэтому ответ уходит
на подделанный `Packet.m_Address`. Коэффициент усиления легко 1:20 … 1:100 на полном сервере →
сервер превращается в reflector для DDoS третьей стороны.
Фикс:
- Для 0.6 (`SERVERINFO_VANILLA`/`SERVERINFO_64_LEGACY`) отдавать по одному пакету и жёстко
  ограничивать суммарный объём ответа (не слать 64_LEGACY multi-chunk без верификации).
- Ввести проверку размера ответа/запроса: не отвечать пакетами, суммарно превышающими N×размер запроса.
- Приоритет — verified-путь (0.7 с ResponseToken, строка 3052-3073), а невериф. 0.6 душить агрессивнее.

### server.cpp:2734-2760 (SendServerInfo, ветка SERVERINFO_EXTENDED)
Проблема: `EXTENDED` вообще не должен отвечать на невериф. connless-запрос — это самый «жирный»
формат (несколько чанков, полный список). Строка 3039 (`Type = SERVERINFO_EXTENDED` при
`NETSENDFLAG_EXTENDED`) позволяет затребовать максимально большой ответ одним маленьким запросом.
Фикс: для EXTENDED требовать verified token либо резать до одного чанка; ограничить суммарный
payload при отсутствии верификации источника.

## 2. Отсутствие / слабость rate-limit на ответы

### server.cpp:2308-2327 (CServer::RateLimitServerInfoConnless)
Проблема: rate-limit ГЛОБАЛЬНЫЙ (единые счётчики `m_ServerInfoNumRequests` /
`m_ServerInfoFirstRequest`), без разбивки по IP источника. Следствия:
- Атакующий одним флудом со спуфнутых адресов выбивает лимит, и легитимные браузеры серверов
  перестают получать инфу (DoS доступности листинга).
- До достижения лимита (`sv_server_info_per_second`=50, `..._replies_per_second`=500 по умолчанию)
  усиление всё равно работает — 500 ответов/сек × размер ответа = заметный отражённый трафик.
Фикс:
- Ввести per-source-IP токен-бакет (напр. хэш-таблица адрес→счётчик с TTL), чтобы один источник
  не мог ни исчерпать глобальный лимит, ни быть эффективно заспуфленной целью отражения.
- Снизить дефолт `sv_server_info_replies_per_second` и учитывать РАЗМЕР ответа (байты/сек), а не
  только число ответов.

### server.cpp:2311 (окно лимита)
Проблема: окно — ровно 1 секунда с жёстким сбросом (`Now > m_ServerInfoFirstRequest + time_freq()`),
т.е. на границе окна возможен всплеск 2× лимита (burst на стыке двух окон).
Фикс: скользящее окно либо токен-бакет с плавным пополнением.

## 3. Неэффективные проверки банов при флуде

### netban.cpp:374-415 (CNetBan::IsBanned) + netban.h:123-132 (CBanPool::Find)
Проблема: проверка диапазонных банов — двойной цикл: по всем длинам префикса (`i` от Length-1 до 0)
× по всей hash-цепочке (`m_pHashNext`). При коллизиях хэша (хэш = сумма октетов & 0xFF —
очень слабая функция, легко коллидируется, см. netban.cpp:13-17) цепочки в одном бакете
могут вырождаться в длинные списки. Под флудом новых соединений IsBanned зовётся на каждый
коннект → O(диапазоны) на пакет. Атакующий, зная слабый хэш, может подобрать адреса в один
бакет и деградировать проверку.
Фикс:
- Усилить хэш (напр. FNV/murmur по октетам вместо суммы) — резко снизит коллизии и длину цепочек.
- Кэшировать результат IsBanned для адреса на короткий TTL, чтобы повторные пакеты со спуфнутого
  адреса не гоняли полный обход.

### netban.cpp:295-313 (CNetBan::Update) — вызывается server.cpp:3126 каждый тик PumpNetwork
Проблема: снятие протухших банов идёт через `First()` + `Print()` в консоль на каждый снятый бан.
При массовых временных банах (напр. авто-баны от антифлуда) это спам в лог/консоль и лишняя работа
в горячем сетевом цикле.
Фикс: батчить/подавлять лог при массовом истечении; выносить чистку из каждого тика.

### netban.h:138 (MAX_BANS = 2048) + netban.cpp:252 ("ban failed (full banlist)")
Проблема: пул банов фиксирован (2048 addr + 2048 range). При флуд-атаке с большого числа адресов
авто-бан быстро заполняет пул → новые злоумышленники уже НЕ банятся ("full banlist"), защита
отключается сама собой. Нет вытеснения старых/наименее значимых записей.
Фикс: для авто-банов от антифлуда завести отдельный пул с LRU-вытеснением и коротким TTL, чтобы
переполнение не блокировало занесение новых адресов.

## 4. Краши / некорректный разбор

### server.cpp:2754 и 2701 (dbg_assert_failed / dbg_assert в путях отдачи serverinfo)
Проблема: `dbg_assert_failed("Invalid serverinfo Type")` (2754) и
`dbg_assert(Packer.Size() <= MaxPacketSize ...)` (2701) в release с включёнными ассертами
аварийно завершают сервер. Тип берётся из внутренней логики, но при регрессии/новом протоколе
это путь к крашу из сетевого кода; ассерт на размер пакета зависит от данных (число/имена клиентов).
Фикс: заменить в сетевом пути на безопасный early-return + лог, а не abort.

### server.cpp:3034-3050 (разбор GETINFO)
Проблема (минор, сейчас закрыто, но хрупко): доступ к байту токена
`((unsigned char *)Packet.m_pData)[sizeof(SERVERBROWSE_GETINFO)]` (строка 3083) безопасен только
благодаря проверке `m_DataSize >= sizeof(...)+1` (3034). Ветка 64_LEGACY (3047) использует ту же
проверку. Любое изменение условия рассинхронизирует границу → OOB-чтение.
Фикс: читать токен через CUnpacker с проверкой Error(), как это уже сделано для sixup-ветки
(3054-3060), а не по прямому индексу.

### serverinfo.cpp:26-40 (ParseCrc / sscanf)
Проблема: `sscanf(pString, "%08x", pResult)` в парсере ответа мастера — при доверии к внешним
данным опасен; здесь длина проверена (==8) и hex-фильтр есть, так что OOB нет, но паттерн
«sscanf по сетевым данным» хрупкий.
Фикс: заменить на явный парс hex без sscanf (str_toint/ручной), убрать зависимость от libc-формата.

### serverinfo.cpp:118-152 (FromJsonRaw, цикл по Clients)
Проблема: цикл идёт по `Clients.u.array.length` (полностью управляется входным JSON) — при огромном
массиве клиентов это CPU-DoS на разбор (валидация каждого элемента) даже несмотря на то, что
хранится лишь SERVERINFO_MAX_CLIENTS. Ошибка в любом элементе возвращает true (ок), но пустой
валидный флуд из тысяч элементов всё равно прогоняется целиком.
Фикс: ограничить число разбираемых элементов (early break после SERVERINFO_MAX_CLIENTS с проверкой
только счётчиков) и/или общий размер входного JSON до парсинга.
